============ 문제점 ===============
멀티 스레드는 최종적으로 command에게 넣기는 하는데 사전 작업을 다 하고, 최종 결과만 Queue에 넣음

1. 입력은 다른 스레드로 빼기에는 렌더링 주기와 안맞으면 버벅이는 느낌이 커서 그냥 동일 메인 루프 에서 처리하도록 했다

2. 스레드 긴 lock을 피하기 위해서 스냅샷을 사용

3. 서로 다른 스레드를 돌리고 각가의 스레드가 사용할 queue를 이용해서 서로 명령을 주고 받는 형식으로 진행

4. 멀티 스레드를 이용해서 렌더링. 다만 다이렉트 11은 immediate는 한놈밖에 없기 때문에 deferred를 사용

5. 메시지 큐로 명령을 받는데 통일된 크기로 하기에는 데이터가 아까움 -> 다형성을 사용하는 방식으로 구현
 그리고 모든 명령을 다루는 클래스를 만들어서 처리

6. 그리는 것 관련해서 DrawResource 를 만들어서 이곳에서만 사용하게 했다. 그리기 전에 동기화
 그래서 그려야 할거, 메시 사라진 경우, 기본 메시 구분하면서 렌더링을 해야 한다

7. 기존 액터 기반을 메시 기반으로 바꾸면 지울 거를 선택 잘해야 했다

8. 로딩창 멀티스레드로 구현 -> command execute 할 때 이거 로딩 걸어야 싶으면 그 실행  thread로 넘기고 로딩을 띄운다
	하나 불러올 때 로딩창을 어떻게? 본래 모델불러오면서 resource 만드는데. 2번 띄우자

9. 명령 체계는 모든 스레드에서 스케줄러에게 넘기고, 스케줄러가 마지막에 렌더링 하기 전에 단일 쓰레드에서 싹 비운다

10. 드로우 디버그 할 때, 매 틱마다 살려두는 거 

11. 레이 트레이싱 할 때 메시따로, 월드 행렬 따로 보관하기에 외부에서 월드 기준으로 오면 제대로 된 비교 힘듬
-> 월드 기준의 좌표와 방향을 자신의 월드 역행렬로 로컬 공간으로 바꿔서 처리

12. 디버그를 그릴 때 자원을 관리 하기 위한 이름을 따로 받았는데, 편의 성을 위해서 매크로를 이용, FILE과 LINE을 이용해서 동일한 코드 위치에서 호출하는 함수에는 자동으로 이름을 부여해서 사용하도록 정리 했다

13. 최적화를 위해, 액터에 변경 사항이 있을 때 전체를 갱신하는것이 아니라 부분 메시만 갱신하는 방법을 쓴다

14. 상대 경로를 처리해서 파일의 현재 디렉토리 처리를 어떻게 할 것인가

15. 액터를 관리 할 때, 이름은 바뀔 수 있어도 자원을 관리하는 ID는 따로 둬야 한다

16. 오일러, 쿼터니언 캐시

17. 에디터 축을 따로 관리하기. 기존에는 드로우 리소스에 담아서 한번에 했는데 그리는 것 따로 처리를 위해서

18. 기본적으로 디버그는 각각의 디버그 마다 드로우 콜을 보낸다. 하지만 이럴 경우, 메시의 바운딩 박스를 표현할 때 디버그 박스를 쓰는데, 이러면 메시의 수만큼 드로우 콜이 많아져서 fps가 떨어지게 된다. 이를 해결 하기 위해서 전체를 하나의 메시로 합쳐서 그렸다

19. 텍스처 캐시 시스템으로 원래 드로우 리소스 마다 따로 srv를 가지고 있었는데 이걸 따로 빼서 동일한 텍스처 사용하면 로딩 시간 줄이기 -> 이걸로 텍스처 로딩 속도를 획기적으로 줄였다. 사실상 상수의 개수

20. 텍스처와 로딩을 다른 스레드로 빼려고 한다. 이를 위해 다른 스레드를 준비한다

아예 다른 메시더라도, 같은 텍스처와 같은  const를 쓴다면 하나의 메시로 합쳐서 그림

22. 물리 엔진과 렌더링의 동기화 - 물리 엔진이 몇배는 더 빠르게 바꾸는데, 그걸 그리는 주기랑 동기화를 시키려고 하면 속도가 느려질 수 있다 -> 더블 버퍼링을 쓰자
